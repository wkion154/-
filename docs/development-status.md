# 개발 단계 현황

## 이서 검색 HTTP 403 보고서 대응

사용자 진단에서 `query=이서`, `search_browser_visible=false`, 제공 파일 미리보기 활성 상태로 `사이트 접근 오류: 403`을 받았다. 페이지·후보·미리보기는 모두 0건이다. 현재 작업자는 알려진 인물 페이지가 없을 때 `/kpics`에서 이름을 선택하므로 목록 진입 시 실패한 것으로 보이지만, 이 과거 보고서에는 실패 URL/단계가 없어 확정할 수 없다. 숨김 모드 때문에 거부됐다고 단정하지 않는다. 해당 검색은 미완료다.

새 작업자 오류에는 실패 단계, HTTP 상태, 페이지 주소와 blocked 여부를 담고 통합 진단의 failure_details까지 전달한다. HTTP 거부는 그대로 중단하며 다른 브라우저 표시 모드나 별칭으로 자동 우회하지 않는다. 기존에는 이름 선택 실패까지 모두 blocked=True로 전송해 등록된 별칭을 시도하지 못했다. 정확한 선택지 부재만 접근 거부와 구분해 등록된 별칭을 다음 계획에서 사용할 수 있게 했다. 임의의 이름/인물 ID는 만들지 않는다. 이전 작업자와의 호환성에서는 알 수 없는 오류를 보수적으로 차단 처리한다.

현재 403을 해결한 것으로 표시하지 않는다. 진단상 다음 비교는 사용자가 명시적으로 켠 [검색 브라우저 표시]에서 같은 검색의 접근 결과다. 표시 모드에서도 거부되면 해당 출처의 실제 접근 제약이 남은 것이며 온라인 검색 완료 조건을 충족하지 못한다.

검사: 관련 22개 통과, 전체 238개 통과·24개 건너뜀(26.59초), `test-results-search-failures.xml`. 실사이트 403 해소나 실제 Windows의 숨김/표시 모드 비교를 검증한 결과는 아니다.

## Windows 표시 성공 이후 속도·검색 창 개선

사용자 화면에서 실제 검색 사진 표시를 확인했다. 여러 사진의 표시 성공은 전체 인물 일치, 전체 수집, 원본 감상/보관, 다중 출처 또는 1단계 완료를 증명하지 않는다.

검색 작업자의 Edge/Chrome 실행은 기본 headless로 바꿨다. 실제 브라우저와 사이트 내부 스크롤은 필요하지만 화면에 나타나지 않도록 한다. [검색 브라우저 표시 (문제 확인용)]를 명시적으로 켜면 기존 표시 모드를 쓴다. Edge 실패 시 Chrome에서도 숨김/샌드박스 설정을 유지하며 자동으로 표시 모드나 샌드박스 해제로 전환하지 않는다. 이 서버에서는 실제 브라우저 실행이 제한되므로 Windows 숨김 모드 실동작은 후속 확인이 필요하다.

사이트 제공 파일의 512px JPEG 미리보기 캐시를 추가했다. 이전의 재표시는 큰 파일 해시 계산과 축소 디코딩을 반복했다. 이제 현재 출처/사진의 표시·파일 다운로드 권한, 관측된 URL, 작은 캐시 해시를 검사해 캐시를 재사용한다. 작은 캐시가 없어지면 기존 제공 파일을 검증해 재생성한다. 원본 보기/영구 보관 경로의 전체 파일 검증은 변경하지 않았다. 큰 파일의 다운로드·사진 수·네트워크 요청 간격은 줄이거나 우회하지 않는다.

재현 가능한 로컬 성능 측정: `python scripts/profile_provided_previews.py docs/provided-preview-profile.json`. 생성한 1,200만 픽셀 PNG와 네트워크 없는 응답으로 이전/새 warm-cache 경로를 7회 측정한다. 실제 Windows·인터넷·첫 다운로드 속도 수치가 아니다. 캐시 변조, 캐시 삭제 복구, 권한 취소, 영구 보관 비실행과 숨김/표시 모드·브라우저 실패 동작을 회귀 검사한다.

측정 결과: 30,587,678바이트 원본과 57,138바이트 작은 미리보기에서 이전 warm 경로 중앙값 0.21656초, 새 경로 0.01188초(약 18.2배). 전체 검사 233개 통과·24개 건너뜀(25.76초), 이후 추가된 설정 전달 검사와 관련 회귀 26개 통과. 앱 기본 실행 검사도 통과했다. `test-results-background-cache.xml`은 전체 검사 결과다. Windows 백그라운드 검색은 아직 실기 미검증이다.

## Windows 미리보기 차단 보고서 대응

사용자 Windows 보고서에서 Kpopping 검색 164개+추가 51개, 갤러리 215개를 확인했다. 검사한 미리보기 3개는 모두 robots에서 차단됐다. 사진 표시 성공으로 세지 않는다. 실제 정책 재검사에서 kpopping.com의 `/api/kpics-image`는 금지, cdn.kpopping.com의 `/kpics/`는 허용이었다(`live-checks/kpopping-preview-policy.json`). robots 응답은 사진 이용권이나 최대 원본 해상도를 증명하지 않는다.

검색 출처 설정에 별도의 사이트 제공 파일 다운로드·미리보기 옵션을 추가했다. 기본은 꺼짐이다. 이를 직접 선택한 경우에만 기존 근거와 함께 출처의 다운로드를 허용하고 새 검색 후보에 사진별 권한을 부여한다. 이미 기록된 사진별 거부/검토는 덮어쓰지 않는다. 미리보기는 표시 권한과 파일 다운로드 권한 양쪽을 검사한 뒤 기존 provided_files.resolve로 정확한 관측 CDN 파일을 임시 캐시에 받아 축소한다. CDN 자체의 robots와 다운로드 제한도 유지하며 차단된 변환 URL은 요청하지 않는다. 기존 검색 ID·즐겨찾기·미리보기 레코드를 교체하거나 영구 보관하지 않는다. 자동 분석/AI 권한을 주지 않는다.

옵션을 끈 상태에서 변환 주소가 차단되면 검색 출처에서 확인할 옵션을 구체적으로 안내한다. 진단 보고서에는 provided_preview_enabled 상태를 추가했다. 전체 225개 통과·24개 건너뜀(25.16초), `test-results-provided-previews.xml`. 새 회귀는 명시적 선택, 출처/사진 권한 분리, CDN 정책 거부, 권한 취소, 기존 거부 유지, 임시 캐시와 영구 보관 구분, 실제 설정 창 연결을 확인했다. 합성 이미지 검사이며 실제 Windows CDN 이미지 표시 성공은 수정본 보고서로 확인해야 한다. 1단계는 계속 진행 중이다.

## 검색 요청과 추가 페이지 처리 수정

Kpopping의 인물/그룹 선택기는 정확한 이름을 요구한다. `identity_search` 출처에는 세션에서 생성한 구도/색상 접미사를 제거한 이름·별칭을 보내도록 했다. 자유 텍스트 검색 출처의 힌트와 갤러리의 분석 필터는 유지한다. 단일/복수 제공처 경로 모두 검사했다.

단일 제공처에서 차단된 세션은 이후 추가 페이지 호출에서도 네트워크를 다시 요청하지 않는다. UI도 차단 시 [더 검색]을 비활성화하며 새 검색을 시작하면 새 세션에서 재시도할 수 있다. 기존 수정은 별칭 재시도만 막았고 동일 세션의 수동 재요청은 남아 있었으므로 이 부분을 보완했다.

다음 페이지 커서는 `None`일 때만 종료로 처리한다. `0`, 빈 객체, 빈 배열, `false`는 그대로 JSON에 보존해 다음 호출에 전달한다. 기존 truthiness 검사로 초기 페이지를 반복할 수 있던 문제를 수정했다. 관련 검색·통합 진단·브라우저 어댑터 검사 33개 통과.

최종 전체 검사 218개 통과·24개 건너뜀(23.57초), `test-results-search-reliability.xml`. 선택적 CV/실제 브라우저 검사는 통과로 집계하지 않는다.

새 게시 환경에서 샌드박스가 켜진 Chromium 실행을 재확인했으나 실패했다(`live-checks/browser-runtime.json`). 앱 기본 실행 검사는 통과했다. 실제 Windows 검색·화면 검증과 1단계 완료는 여전히 미완료다. 다음 실사이트 증거는 `CHECK_SEARCH_WINDOWS.bat`의 보고서와 화면 확인이다.

## 기존 앱 경로의 Windows 통합 진단 추가

`CHECK_SEARCH_WINDOWS.bat`와 `python -m app.search_check`를 추가했다. 기존 SearchService, LibraryRepository/LibraryService, WebService.download를 사용한다. 기본은 검색 2배치와 최대 3개 미리보기의 실제 디코딩까지 확인하며 제공 파일은 `--check-files`, 영구 보관은 추가로 `--save`를 명시한 경우에만 검사한다. 출처/사진 권한은 기존 설정을 사용하고 자동 부여하지 않는다. 사용자 입력은 배치 명령문에 삽입하지 않고 환경을 통해 Python에 전달한다.

앱과 같은 데이터 잠금을 획득하며, 기존 라이브러리가 없거나 앱이 열려 있으면 오류 보고서를 만든다. 출처별 검색 오류, 갤러리 수, 미리보기/제공 파일 크기, 선택적 저장 결과를 JSON으로 남긴다. 미리보기만 열리면 파일 검사는 실패로 기록한다. 검사 범위 통과와 GUI 조작/인물 일치/1단계 전체 완료를 구분한다. 사진/검색 결과는 기존 라이브러리와 캐시에 정상 경로로 기록될 수 있으므로 순수 읽기 전용 도구로 표시하지 않는다.

합성 파일로 기존 갤러리 연결, 권한 비변경, 미리보기의 파일 위장 방지, 파일 검사와 영구 보관 분리, 검색 실패/범위 제한을 검증했다. 실제 Windows 배치 실행은 이 Linux 서버에서 검증하지 못했다. 기존 단독 웹 접속 진단과 실제 앱 처리 경로를 구분한다.

최신 전체 검사: 211개 통과·24개 건너뜀(23.73초), `test-results-search-pipeline.xml`. 실사이트 메타데이터 재검사 결과는 `live-checks/search-pipeline-readiness.json`: Kpopping 페이지 접근 성공/인물 필터 미검증, Flickr robots 차단 상태를 재확인했다. Windows에서 새 통합 진단을 실행한 보고서와 실제 화면 확인이 다음 증거다. 환경 재게시 자체는 이 Windows 실행 검증을 대신하지 않는다.

## 후속 검색 연결 보강

기존 수정은 유지하고 Kpopping의 실제 화면 필터 검사를 추가했다. 공개 Kpics JavaScript에서 `idol`/`idolName`, `group`/`groupName` 상태와 선택된 대상의 `Filtering: 이름` 버튼을 확인했다. Windows 작업자는 해당 버튼의 표시를 기다리고, 각 스크롤 회차에도 이름과 표시 상태를 확인한다. URL만 남아 있고 실제 필터가 적용되지 않은 경우, 숨겨진 표시, 다른 대상 표시를 결과로 수집하지 않는다. 작업자 응답에 필터 확인 증거가 없는 경우에도 기존 DB에 후보를 넣지 않는다.

사이트가 생성한 그룹 URL도 처리하며 같은 값의 인물 ID와 그룹 ID는 커서를 공유하지 않는다. 인물·그룹의 혼합 지정이나 중복 ID/이름은 거부한다. 기존 인물 커서 형식은 유지한다. 그룹 자동 선택의 실사이트 성공을 확인한 것은 아니다.

검증: 검색 관련 38개 통과, 이후 최종 전체 검사 202개 통과·24개 건너뜀(26.68초). Qt 앱 기본 실행 검사와 ZIP 매니페스트/해시 검사도 통과했다. 앞선 전체 검사에서 기존 작업 객체 해제 테스트가 한 번 실패했다. 해당 테스트는 단독 재검사와 최종 전체 검사에서 통과했으나 간헐적인 해제 타이밍 문제 가능성은 남긴다. 선택적 CV/브라우저 테스트의 건너뜀은 통과로 세지 않는다.

이 Linux 서버에 Playwright 1.62.0과 Chromium을 설치했지만 `chromium_sandbox=True` 실행은 `No usable sandbox`로 실패했다. 샌드박스를 끄지 않았다. 따라서 실제 화면과 Windows 실행에 대한 검증은 남아 있다. 공개 스크립트의 구조 확인은 실제 사진 검색/표시 성공과 구분한다.

## 게시된 환경에서 재검사 (2026-10-28 21:42 KST)

이전의 환경 프록시 접속 차단은 해소됐다. `scripts/check_search_readiness.py --output docs/live-checks/resume-search-readiness.json`을 실행해 앱과 같은 HTTP/robots 코드로 확인했다. 진단은 사용자 라이브러리나 권한을 바꾸지 않고 사진을 다운로드하지 않는다. 완료 증거가 아니므로 종료 코드는 2다.

- Kpopping: 기존 인물 URL의 HTML 읽기 성공. 제목은 일반 사진 목록이며 이미지 요소 17개가 관측됐다. URL에 인물 ID가 있다는 사실만으로 필터 적용을 인정하지 않는다. Windows 브라우저에서 실제 선택 상태·이미지 후보·뷰어·저장 검증이 남아 있다.
- Flickr: 공개 피드는 HTTP로 응답하지만 현재 robots의 기본 규칙은 `Disallow: /`이다. 앱의 정식 읽기 경로는 메타데이터 요청을 차단했다. 다른 User-Agent로 바꾸거나 정책을 무시하지 않는다. 현재 사용 가능한 검색 출처로 완료 처리할 수 없다.
- 진단 회귀와 검색/스크롤/제공 파일 검사 29개 통과. 단계 1은 계속 미완료이며 단계 2·3은 미착수다. 이전 프록시 차단 설명은 과거 기록으로 읽는다.

| 3. 자동 갱신·최적화·Windows 배포 | 미착수 | 실제 신규 사진 갱신, 대량 결과 최적화, 전체 회귀 및 Windows 실행본 제작·검증 |

현재 1단계의 마무리가 필요하며 **그 이후 단계는 2·3단계, 두 개**다. 완료한 단계는 아직 0개다. 앞선 작업을 두 번 수행했다고 2단계까지 완료한 것으로 기록하지 않는다. 이후 보고에도 현재 단계의 완료 여부와 이후 단계 수를 함께 명시한다.

이번 회차에서 완료한 구현은 사이트가 실제로 제공한 파일 URL의 추출·권한 검사·실측 캐시·기존 뷰어/영구 보관 연결이다. Kpopping의 관측된 /api/kpics-image 주소 안에 제공된 정확한 cdn.kpopping.com/kpics/ 주소만 사용한다. 최대 원본 해상도를 확정하지 않으며 파일명/크기 주소를 합성하지 않는다. 원본·실측용 다운로드는 출처와 사진 양쪽 권한을 확인한다.

작은 미리보기와 제공 파일은 기존 web_revisions에서 같은 이미지의 별도 파일로 관리한다. 제공 파일을 저장해도 기존 검색 결과는 연결된 자산 하나를 표시하며 즐겨찾기와 발견 순서를 유지한다. 사진별 권한을 취소하면 저장본의 보기에도 반영한다. 분석·AI 권한을 자동 허용하지 않는다. 큰 파일 주소를 확인하지 못한 미리보기는 원본으로 저장하지 않는다.

전체 회귀 213개 통과, 35.43초. 마지막 저장 상태 문구/반환 플래그 보강 후 관련 36개도 통과했다. 네트워크 없는 브라우저 fixture와 직접 생성한 소형/대형 PNG를 사용했으며 실사이트 성공 증거가 아니다. `test_provided_files.py`는 주소 검증, 미리보기 권한과 다운로드 권한 분리, 실제 파일 크기 판독, 캐시 변조/권한 취소, 중복 보관 방지, 검색/즐겨찾기 유지까지 검증한다. DB 메타데이터 성능을 같은 가상 10,000개/검색 1,000개 조건으로 재측정한 중앙값은 약 0.03415초였다. 네트워크·이미지 디코딩·Windows UI 시간은 포함하지 않는다.

실사이트 검증의 외부 조건: 현재 클라우드 네트워크는 제한 정책 enforced/custom allowed_hosts 비어 있음 상태다. 저장된 환경 네트워크 초안은 게시/적용되지 않았으며 이 작업에서 권한을 우회하지 않았다. Windows 앱의 실제 다중 출처 표시·제공 파일 접근·그룹/솔로 자동 선택은 미검증이다. 이전 사용자 보고서의 Kpopping 목록 HTTP 200은 관측 증거일 뿐 이번 앱의 전체 흐름을 검증한 것이 아니다.

이번 회차에 기존 8개 검색·조사 호스트를 보존하고 cdn.kpopping.com, live.staticflickr.com, farm1.staticflickr.com~farm9.staticflickr.com을 환경 네트워크 초안에 추가했다. 도구는 status=saved/requires_publish=true를 반환했다. 재개 안내도 현재 구현·단계 상태에 맞춰 저장했다. 기존의 관련 없는 게임 설치 스크립트와 저장소 설정은 수정하지 않았다. 사용자 환경 설정에서 검토·저장·게시한 후 런타임 적용과 실제 요청을 다시 검증해야 한다.

이번 ZIP은 실험용 소스 실행본이다. 실제 Windows EXE 또는 정식 완료판으로 표시하지 않는다. 코드가 더 추가되었다는 이유로 1단계나 후속 단계를 완료 처리하지 않는다.
