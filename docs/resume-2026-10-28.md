# 20:13 저장본에서 작업 재개

후속 환경 게시 후 접속 차단은 해소됐다. 최신 실제 접근 결과는 `live-checks/resume-search-readiness.json`과 `development-status.md`의 21:42 KST 항목에 있다. 아래 "남은 외부 조건"의 프록시 403은 게시 전 관측이다. 새 진단/검색 관련 검사 29개 통과. Flickr는 현재 robots에서 차단되며 Kpopping은 Windows 브라우저의 실제 필터/뷰어 검증이 남아 있다.

기준 커밋: `a67eaed54db4e3b7d95dd30a8c53f1957bb4c3dc`.

## 수정

- Kpopping 어댑터는 이번 브라우저 배치의 URL에 해당하는 기존 사진만 발견 순서대로 반환한다. 이전에는 페이지 전체에서 최대 1,000개를 다시 반환하여 오래된 후보가 섞이고 큰 배치가 잘릴 수 있었다. 새 조회는 400개씩 나눠 수행하며 다른 페이지의 사진을 섞지 않는다.
- 검색 제공처가 하나일 때도 접근 차단을 받으면 별칭별 재시도를 중단하고 검색 세션을 blocked로 남긴다. 일시 오류의 기존 별칭 진행은 유지한다.

## 검증

- 검색·브라우저·스크롤·제공 파일 회귀: 27개 통과.
- 전체 검사: 191개 통과, 24개 건너뜀 (23.89초). 선택적 CV/브라우저 의존성과 실행 설정이 없는 항목은 검증하지 않았다.
- Linux offscreen 실행 검사: 갤러리와 썸네일, SQLite 무결성, 즐겨찾기 유지, 설정 저장, 오프라인 설정 모두 통과.
- 신규 회귀는 합성 데이터로 1,005개 배치, 다음 배치 순서, 과거 결과 제외, 빈 배치, 단일 제공처 차단을 검사한다. 실제 사이트 성공 증거는 아니다.

## 남은 외부 조건

현재 실행 환경에서 Kpopping과 Flickr HTTPS 연결은 프록시 CONNECT 403이다. 검색에 필요한 두 사이트와 이미지 CDN 13개 호스트를 환경 초안에 저장했고 도구가 saved/requires_publish=true를 반환했다. 환경 설정 검토·저장·게시 후 런타임 상태와 실제 요청을 다시 확인해야 한다. Windows Kpopping 브라우저 작업자는 이 Linux 환경에서 실행할 수 없다.

1단계는 계속 진행 중이다. 실제 여러 출처에서 이름/그룹/솔로 검색, 사진 표시, 추가 검색, 제공 파일 보기와 저장을 확인한 후에만 완료 처리한다. 2·3단계는 미착수다. 이번 실험 ZIP은 Windows 소스 실행본이며 EXE가 아니다.
